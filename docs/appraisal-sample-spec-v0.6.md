## 1. 1件の形式（JSON）

```json
{
  "sample_id": "uw-000001",
  "spec_version": "0.6",
  "input": {
    "event_text": "BがAに近づいたが、Aは距離を取った。",
    "perspective": "B",
    "actor": "A",
    "target": "B",
    "target_category": "相棒へ",
    "relationship": "同じ箱庭で暮らす相手。",
    "state_before": {"joy": 0.31, "sadness": 0.05, "anger": 0.03, "fear": 0.12, "surprise": 0.0, "affection": 0.79, "trust": 0.52, "fatigue": 0.1},
    "char_profile": {"joy": 1.0, "sadness": 1.0, "anger": 0.5, "fear": 1.5, "surprise": 1.0, "affection": 1.0, "trust": 1.0, "fatigue": 1.0}
  },
  "output": {
    "verdict": "change",
    "deltas": {"fear": 3, "sadness": 1}
  },
  "label_source": "table",
  "label_version": "rule-1",
  "source": "sim",
  "provenance": {
    "generator": "underworld-sim",
    "generator_commit": "…",
    "decoder_version": "0.2.0",
    "seed": 42,
    "run_id": "seed42-100d",
    "config_hash": "…",
    "template_id": "react_avoided/v1",
    "axis_values": {"subject_drop": true, "register": "plain"},
    "char_thresholds": {"interrupt": 0.35},
    "source_event": {"type": "REACT", "kind": "avoided", "step": 1234}
  }
}
```

- **出力は点数のみ**（判断①で確定）：減衰・日次枠・関係層はエンジン側の決まった計算であり、モデルには持たせない。`deltas` は整数ポイント。**範囲は −4〜+4**（§9.4 で変更。JSON Schema もこれに合わせる）。
- **判定の3値**：出力は `verdict` ∈ {`change`, `no_change`, `abstain`}。組み合わせの決まりは次の通りで、JSON Schema で検査する。
  - `change`：`deltas` に 0 でない次元が1つ以上ある。**0 の次元は `deltas` に入れない**。
  - `no_change`：判定した結果として変化なし。`deltas` は空 `{}`。
  - `abstain`：情報が足りず判定しない。`deltas` 自体を持たない。
  - `no_change` と `abstain` は別物として、評価でも別に数える。
- **視点**：`perspective` は「感情が動く側」。1件ごとに明記する。
- **actor / target の向き**：総則は「`actor` は出来事を起こした側、`target` は働きかけを受けた側」。この総則は実データと本番のために残す。**シム由来サンプルでは §9.5-2 の決め方を優先する**（相手の側を actor、感情が動く側＝perspective を target にそろえ、target_category はすべて「相棒へ」）。上の例はこの決め方にそろえた（REACT/avoided：近づいた B が perspective＝target、距離を取った相手 A が actor）。
- **個体の id と区分は別の欄**：`actor` / `target` は個体の id（シムでは "A" / "B"、本番では相棒・利用者などの識別子）。区分は `target_category` に分ける。
- **target_category の決め方**：シム由来サンプルでは全件 `相棒へ`（§9.5-2）。実データ・本番では perspective と target の関係から機械的に決める（target が perspective 本人なら `相棒へ`、target が利用者なら `利用者自身へ`、それ以外は `ほかの人へ`）。「ほかの人へ」「利用者自身へ」は評価セットと実データで扱い、評価セットには必ず含める（§9.5-2）。
- **relationship は事実だけを書き、常に入れる**：間柄・続柄などの事実のみを書く。「好意は高め」のような気持ちは書かない（気持ちは `state_before` にだけ置く）。**シム由来サンプルでは全件同じ文にし、日数は入れない**（§9.5-5。日数は日ごとに変わり、シムだけの手がかりになるため）。上の例の「同じ箱庭で暮らす相手。」がその文。
- **個体差は入力に入れる**（判断②）：`char_profile` は次元別係数の**数値**を正本とする（例は上記 JSON）。係数は **低い ×0.5／ふつう ×1.0／高い ×1.5** の3段階のみとし、モデルへ渡すときは段階と1対1の固定文型で文章化する（言い換えはしない）。
  - **ラベルは係数を掛けたあとの点数**。作り方は §9.4 の手順に固定する：シムの点数（係数の前）を ±3 に収める → その次元の係数を掛ける → 0.5 はゼロから遠い側へ丸める → ±4 に収める → 0 の次元は落とす → 全部 0 なら `no_change`。
  - **丸めの向き**：0.5 はゼロから遠い側へ丸める（0.5 → 1、−0.5 → −1）。Python の `round()` は偶数丸めで 0.5 → 0 になるため**使わない**。丸めの関数は自前で書き、テストを付ける。
  - **本番でエンジンは係数を二重に掛けない**：モデルが出す点数は係数適用済みであり、エンジンはそのまま感情の状態へ加算する。
  - **閾値は char_profile に入れない**：閾値（割り込み閾値など）は行動を変えるだけで点数を変えないため、`provenance.char_thresholds` に記録するにとどめる。
  - 係数を入れない場合、同じ入力に矛盾する正解が付き、データが壊れる。個体ごとに係数を変え、中立のままにしない（判断②、Phase 1 から効かせる）。
- **文脈は正解に効くものだけ**（判断③）：`state_before` は §3 の凍結対象リストにある種別でのみ入力に含める。`recent_context` はシムの正解に効かないため、シム由来サンプルには原則として付けない（上の例にも付けていない）。例外は §6 の「2割は欄を付けたまま学習」のときだけ。
- **慣れの回数の欄**（§9.3-3）：CONTACT の「一緒に過ごす」の件には、入力に `contact_streak`（続けて顔を合わせた回数）の欄を足し、固定文型で文章化する。数え方は §9.3-3 に固定する。
- **event_text への答えの漏れ禁止**（重大）：記号ログには理由や数値（「好意が強く」「喜び+0.15」）が入っているが、デコードした文に perspective 側の気持ちや増減が残ると、答えが問題文に書いてある状態になる。event_text は「外から見えた出来事だけ」にし、気持ちは `state_before`（構造化）にだけ置く。ただし感情が動く側の**見えるふるまい**（謝った・距離を取った等）は出来事として書いてよい（§9.5-2）。デコーダーの単体テストで、感情語と数値が event_text に入らないことを検査する。
- **ラベルの出どころ**：`label_source` ∈ {`table`（シムの点数表と §9.4 の手順）, `human`（人）, `open_model`（オープンな重みのモデル）} に加え、`label_version` を持つ。人のラベルには `annotator_id`。ホストLLM（Claude等）の判定はラベルにしない。
- **label_version の意味と命名**（§9.5-7、§10.4 で改名）：`label_version` は「正解の決め方の版」とし、仕様の版（spec_version）とは分けた名前で持つ（例：`rule-1`。§9.4 の仮の値を変えたら `rule-2`… と上げる）。`table_version` は廃止し、出どころの版管理は `generator_commit` と `config_hash` に任せる。
- **source の3値**：`source` ∈ {`sim`, `real`, `human_written`}。`real` は抽象化した文だけを持ち、生の文は本人のPC内の別置きへの参照（`raw_ref`）にとどめ、repo に入れない。
- **abstain の学習例の出どころ**：変換表からは abstain が出ない。学習用の abstain は、(a) 人がラベルを付けるときに「判定できない」を選んだ**学習側の**件、(b) 情報が欠けた出来事として人が書き、人が abstain と付けた件、の2つから作る。**評価セットの件は学習に使わない**（§5、凍結条件 (a)）。件数の見込みと足りないときの扱いは §5 に書く。

## 2. 記号ログ→文章のデコード方針

- **actor の決め方**：シム由来サンプルでは §9.5-2 の決め方（相手の側を actor、perspective を target）を使う。実データ・本番では §1 の総則（actor＝出来事を起こした側、target＝働きかけを受けた側）を使う。v0.4 の種別ごとの当てはめ表は、シム由来サンプルについては使わない。
- イベント種別×kind ごとに文型テンプレートを持つ（例：REACT/avoided → 「{target}が{actor}に近づいたが、{actor}は距離を取った」）。テンプレートには ID と版を持たせ、`provenance.template_id` と軸の値（`axis_values`）を刻む。
- **文に必ず出すもの**（§9.5-4）：挨拶での相手の様子（にこやか／ふつう。greet_met と greet_calm を分けるため）、謝罪の結果、摩擦の強さ（§9.3-1）、距離を取ったのは誰か、「目が合った」か「見えた」か。
- **型は外から見える属性だけで選ぶ**：`template_id` に感情の名前や理由（例：`react_avoided_affection`）を入れない。好意などの見えない理由で型を選ぶと、言い回しの違いから答えが漏れ、感情語・数値の検査ではつかまらない。型の選択が **perspective 側の** state と結びついていないことを、テストで確かめる（同じ出来事に違う state を付けても、選ばれる型が変わらないこと）。相手の見える様子は出来事の一部として型を分けてよい（§9.5-4）。
- 言い換えの多様性は「型の軸」で持つ：主語の省略、語尾、時制、距離感の表現などを軸として組み合わせる。型と軸の値の取り置きは §4 の順序（run の側を先に決める）に従う。
- **型の本数**（§9.5-6）：種別×kind ごとに型は **3つ以上** 用意し、学習・検証・テストに各1つ以上を割り当てる。**検証側にも専用の型を取り置く**。
- event_text は外から見えた出来事だけ（§1の漏れ禁止）。デコーダーの単体テストで感情語・数値の混入を検査する。
- シム由来サンプルの役割は「言い換えへの強さ」の練習台。本番の担当範囲（シート外の出来事）は実データ側が担う。
- 評価セットには、テンプレートを通らない **人が書いた文** を必ず含める（§5）。

## 3. 文脈フィールドの線引き（凍結対象）

§9.5-3 で確定した一覧を凍結対象とする。v0.4 の「コードから機械的に作る」見当は、この一覧で置き換える。

- **state_before が正解に効く種別は次の5つ**。これらでのみ `state_before` を入力に含める。
  - NOTICE：相手への支配的な気持ち・0.7以上の上乗せ
  - LOST_SIGHT：支配的が好意か不安か
  - REACT/avoided：近づいた気持ちが怒りか
  - CONTACT/greet：自分の支配的
  - CONTACT/keep_distance：自分の支配的が不安か
- **履歴で正解が変わる種別はない**。慣れは §9.3-3 の専用欄（`contact_streak`）で扱い、根に持つは §9.3-2 でサンプルから除外する。
- **recent_context はシムの正解に効かない**。シム由来サンプルには原則付けず、§6 の「2割は欄を付けたまま学習」の例外でのみ付ける。
- `relationship` は線引きの対象にしない（§1 の理由による）。

## 4. 分割ルール（学習／検証／テスト）

- **順序：run の側を先に決める**。run（seed と気質＝係数の組み合わせの組）を学習／検証／テストのいずれかに割り当て、その run のサンプルは、**同じ側に割り当てた型・軸の値だけでデコードする**。この順序なら、run・型・プロファイルの割り当てが衝突することはなく、捨てるサンプルも出ない。
- 型（テンプレート）と軸の値も側ごとに割り当てる。テスト側の run はテスト側の型・軸だけでデコードされるため、学習データにテスト用の言い回しは現れない。検証側にも専用の型を取り置く（§9.5-6）。
- **気質（係数の組み合わせ）も分割の軸にする**（判断②）：run ごとに係数の組み合わせを変え、**テスト用の組み合わせを丸ごと取り置く**。毎回同じ気質だと、個体単位で分ける意味がなくなるため。気質は run にひも付くので、run の割り当てがそのまま気質の割り当てになる。
- **同じ出来事から作る A 視点と B 視点の2件は、必ず同じ分割に入る**（同じ run から作られるため自動的に満たされる。テストでも確かめる）。
- テスト分は開発中に見ない本番テストとして凍結する。
- 実データ（Phase 3）は出どころ単位で分割し、評価セットは人のラベルのみで構成する。
- 仕様には `spec_version` を持たせ、JSON Schema を repo に置いて、全サンプルをテストで検査する（§1 の verdict と deltas の組み合わせ、deltas の範囲 −4〜+4 も Schema で縛る）。

## 5. 評価セット（Phase 1直後に前倒しで着手）

- まず **300件** 規模（判断④）。ただし差を言うには少ないので、数字には区間（ブートストラップ等）を付け、「試験版」と明記する。
- **構成は「シート外の出来事が主、シート内の言い換えは対照」**（目安：シート外 210件／対照 90件）とし、結果も分けて報告する。モデルの本番の仕事はシート外である。
- **評価セットの件は学習に使わない**（凍結条件 (a)）。評価セットの中で「判定できない」と付いた件も、評価専用であり、abstain の学習例には回さない。
- **学習用 abstain の件数の見込み**：学習データの総量は Phase 2 の収穫量で決まる。総量 10,000件なら 5% は 500件であり、人手だけで作ると重い。まず **200件を目標** に人が作り、総量に対する割合が 5% に届かない場合は、(1) 割合を下げる（1〜2%）代わりに学習時に abstain の例へ重みを付けて補う、(2) それでも足りなければ Phase 3 の実データ側の人のラベル（学習側の分）から補う。無理な水増しはしない。
- **問題文を書く分担案**（判断④・追加分）：全部をきなこが書く形にはしない（「人が書いた文」が要るため）。
  - ぷゆんの書き下ろし：120件
  - きなこの叩き台 → ぷゆんが自分の言葉に書き直し：90件
  - 協力者2名：各45件（ただし、**自分が書いた文には自分でラベルを付けない**）
- **書き手の出どころは分けて記録する**：90件の「AIの叩き台あり」は、他の書き下ろしと provenance で区別する（例：`writing_origin` ∈ {`puyun`, `ai_draft_rewritten`, `collaborator`}）。分析のときに書き手で分けて見られるようにするため。
- **ラベル付けと書き手の決まり**：ぷゆんは自分が書いた分を含む全件にラベルを付ける（300件を通した一致度の基準になるため）。ただし自分が書いた文であることは `writing_origin` で記録され、分析で分けて見られる。協力者には同じ決まりを課さない理由：協力者のラベルは独立した照合のためにあり、本人が書いた文へのラベルは独立性を欠くため。
- **ラベルを付ける人の時間の目安**（判断④・追加分）：1件あたり8次元を7段階から選ぶ形で、**1件 1〜2分**。100件で **約2〜3.5時間**（数回に分けてよい）。ぷゆんが300件すべてに付ける場合は **約6〜10時間** で、日を分ける前提。
- **協力者に頼むとき、先に伝える3つ**（判断④）：(1) かかる時間の目安（上記）、(2) 付けたラベルは **名前を出さずに公開されうる** こと、(3) 出来事は **すべて架空** であること。
- ラベルの付け方：次元ごとに「−強／−中／−弱／0／+弱／+中／+強」の7段階（−3〜+3）で、**「ふつうの気質なら」の強さ** を付ける。係数はあとから §9.4 と同じ手順で機械的に掛けて正解にする（§9.4）。「判定できない」の選択肢も用意し、選ばれた件は評価上の abstain として数える（学習には回さない）。
- **ラベルを付ける人に気質を見せない**（§10.2）：人がラベルを付ける画面・用紙には `char_profile` を出さない。「ふつうの気質なら」で付け、係数はあとから機械的に掛ける。「気質の文は無視して」と頼むより、見せないほうが確実に係数の二重掛けを防げるため。
- 一致度：次元ごとの向き（+・0・−）の一致率を主、Krippendorff の α（順序尺度）を副とする。
- 第三者ラベル：**100件を、ぷゆん以外の身近な2人** にも付けてもらい一致度を出す（判断④）。有料の外注は試験版の結果を見てから判断する。
- 凍結条件：(a) 学習データと別の出どころ (b) 人のラベル (c) 学習前に凍結 (d) 本番テストの取り置き。
- 外部の物差しとして WRIME を評価のみに併用する。ただし **WRIME は書き手の気持ちの強さであり、こちらの「出来事による変化」とは別物**。対応のさせ方：perspective は書き手本人とし、重なる6次元について **向き（その次元の気持ちが表れているか）だけ** を比べる。数字は **参考値** として扱い、合否の判定には使わない。affection・fatigue は WRIME に無いため対象外と明記する。研究目的のみ・再配布禁止のため、学習にも repo にも入れない。
- ベースライン：変換表、汎用LLM（小・大）、日本語BERT系（非LLM）。BERTに勝てなければ「LLMである理由」が立たない。

## 6. 本番でエンジンがモデルに渡すもの

本番の出来事には種別がないため、線引き（§3）は学習側だけの決まりとし、**本番ではエンジンが毎回、決まった欄をすべて渡す**：

- 渡すタイミング：感情エンジンが変換表に無い出来事（シート外）の判定が必要になったとき。
- 渡す欄：`event_text`（出来事の文章）、`perspective`（原則として相棒）、`actor` / `target` の id（総則で決める。§1）、`target_category`（perspective との関係から機械的に決める。§1）、`relationship`（事実のみ）、`state_before`（その時点の8次元）、`char_profile`（相棒の係数、固定文型で文章化）、`recent_context`（同じ日の直前5件まで、固定文型）、`contact_streak`（続けて顔を合わせた回数。**本番での扱いは §9.6 で決める**）。
- **学習と本番のずれへの手当て**：§3 でフィールドを落とす種別についても、サンプルの **2割** はフィールドを付けたまま同じラベルで学習に含める。本番で欄が常に埋まっていても、モデルが壊れないようにするため。recent_context はこの手当てでのみシム由来サンプルに付く（§3）。
- エンジンはモデルの出力（係数適用済みの点数）をそのまま状態へ加算し、係数を二重に掛けない（§1）。
- **本番の前提作業**：エンジンのプリセットには、次元ごとの gain と出来事の種類ごとの係数がすでにある（§9.6）。3段階にそろえる作業ではなく、**3段階に入らない値の扱いを決める** ことが Phase 3 の前の決定事項であり、§9.6 に置く。

## 8. 判断4点（ぷゆんの決定、2026-11-13）

1. **出力**：点数のみ（verdict の3値つき）で確定。
2. **char_profile**：次元別係数まで入れ、Phase 1 から効かせる。係数は個体ごとに変え、run ごとに気質を変えてテスト用の組み合わせを取り置く。段階は3段階（低い／ふつう／高い）で文型と1対1。ラベルは係数適用後の点数とし、丸め方と目盛りの上限を §1 に明記。本番でエンジンが係数を二重に掛けない。閾値は点数を変えないので char_profile ではなく provenance に記録する。（※丸めと上限の具体的な手順は、2026-11-21 の決定 §9.4 で置き換えた。）
3. **文脈の線引き**：シムのコードで履歴・状態を読んで増減を決めている種別だけ。コードから機械的に一覧を作る（§3）。

## 9. 追加の決定（ぷゆんの決定、2026-11-21）

先生の凍結前確認（シムのコード e8287fa と seed42 の100日ログの突き合わせ）を受けての決定。§8 の判断4点はそのまま残し、本節が §1〜§6 の該当箇所を上書きする。

### 9.1 正解と state_before の出どころ

- 正解（deltas）と state_before は、**シムが出来事ごとに記録した値** から作る。ログの effects（0〜1に切ったあとの実際の増減）からは作らない。
- シムのログを v2 にし、出来事ごと・関わった個体ごとに次を足す：
  - 切る前の点数（慣れの割引のあと。**係数の前と、係数を掛けたあとの両方**）
  - その出来事の直前の8次元（state_before の正本）
  - 恨みで点数が変わったかの印（§9.3-2 の除外判定に使う）
- 関わった個体は、**点数が全部0でも記録する**（no_change と「関わっていない」を分けるため）。
- **「関わった個体」の決め方**（§10.4）：片方だけが感じる出来事（NOTICE・LOST_SIGHT・REACT）は**感じた側だけ**。CONTACT・FRICTION・FIGHT・APOLOGY は**二人とも**。見られた側や避けた側に、意味のない no_change を作らないため。
- 理由：effects は切ったあとの値で、100日ログでは起床の疲労が200件中166件、喧嘩の好意が174件中144件、表の点数と違っていた。state_before は出来事ごとの記録がなく、ERODE は一部しか書かれないため、ログから正確に戻せない。

### 9.2 係数はシムの中でも掛ける

- 点数を足すところで、その次元の係数を掛けてから状態に足す。掛けるのは**点数だけ**で、半減期・閾値・ERODE には掛けない（エンジンの gain と同じ範囲）。
- 係数が全部1.0なら現行と同じ動きにする。seed42 のログが、足した欄以外は一致することをテストで確かめる（このテストは §9.3-1 の現行のやり方＝二人別々のサイコロの設定で行う）。
- run ごとに出来事の種類の数を記録する（§9.4 の確認材料）。

### 9.3 入力だけでは正解が決まらない仕組み

線引き：**見える事実から来る仕組みは入力に出す。気持ちの内側だけの仕組みは外す。**

#### 9.3-1 摩擦：サイコロを「受け取り方」から「出来事の強さ」へ

- 一つの摩擦ごとに強さを3段階（軽く／ふつうに／強く）から**一度だけ**選び、二人に同じ値を使う。
- 強さはログに残し、段階と1対1の固定文型で event_text に出す（見える事実なので漏れではない）。
- シムの中では、摩擦の怒りは **2・5・8** で動かす（仮の値。怒りのいちばんの種なので、シムの動きは弱めない）。**正解を作るときだけ**、強さの段階（軽く1・ふつうに2・強く3）を怒りの「係数の前の点数」として使う（§9.4、§10.1）。摩擦の信頼（−2）は今までどおり。
- 受け取り方の違いは係数が担う。
- 現行のやり方（二人別々のサイコロ）は設定で残し、**データを作るときだけ** 新しいやり方にする。§9.2 の「係数1.0で現行と一致」のテストは、現行のやり方の設定で行う。

#### 9.3-2 根に持つ：仕組みは残し、効いた件は外す

- 仕組みはシムに残す。
- 恨みで点数が変わった件（喜び・好意のプラスの ×0.4、気づいたときの再燃）は**サンプルから外す**。外すかどうかは §9.1 の印で決める。

#### 9.3-3 慣れ：仕組みは残し、回数を入力に出す

- 仕組みは残す。
- 「続けて顔を合わせた回数」を入力に1欄（`contact_streak`）足し、固定文型で文章化する。
- 数え方はシムと同じ：前の接触から4時間以内に続いた接触を、今回を含めて数える。挨拶や喧嘩も含む。
- 割引が底を打つ **6回目以上はまとめる**（欄の値は 1〜5 と「6回目以上」）。
- この欄は「一緒に過ごす」（CONTACT/together）の件に付ける。

### 9.4 点数の幅と係数

- **正解の手順**（固定）：シムの点数（係数の前）を **±3 に収める** → その次元の係数を掛ける → **0.5 はゼロから遠い側へ丸める** → **±4 に収める** → 0 の次元は落とす → 全部0なら `no_change`。
- **段階のある出来事の扱い**（§10.1）：段階のある出来事は、**段階をそのまま係数の前の点数にする**（いまは摩擦の怒りだけ。軽く1・ふつうに2・強く3）。正解の例（係数 ×0.5／×1.0／×1.5 の順）：軽く **1／1／2**、ふつうに **1／2／3**、強く **2／3／4**。
- deltas の範囲は **−4〜+4**（JSON Schema もこれに合わせる。§1・§4）。
- **人のラベル** は「ふつうの気質なら」の強さを7段階（−3〜+3）で付け、係数はあとから同じ手順で機械的に掛ける（§5）。
- **仮の値**（最初の試しのデータで先生が確かめる。変えるときは label_version を上げる）：
  - 係数：×0.5／×1.0／×1.5
  - 係数前の上限：3
  - 正解の上限：4
  - 摩擦の点数：シムの中は 2・5・8、正解では段階 1・2・3
  - 慣れの境目：6回目
  - 確認する材料：気質ごとの点数の出方、上限に当たった件数、run ごとの出来事の数（§9.2）、謝罪の場面の数
- 理由：±3 で切ると、点数5以上の次元（喧嘩・強い摩擦・謝罪を受け入れたとき・避けられたときの怒り）では係数がまったく効かなかった（×0.5 も ×1.5 も 3 になった）。

### 9.5 先生がコードから作った一覧と小さな直し

#### 9.5-1 サンプルにする出来事

- サンプルにするのは：NOTICE、LOST_SIGHT、REACT（avoided・mutual_approach）、CONTACT（greet・together・keep_distance）、FRICTION、FIGHT、APOLOGY。**関わった個体ごとに1件**（点数が全部0なら no_change）。「関わった個体」の決め方は §9.1（感じる出来事は感じた側だけ、それ以外は二人とも）。
- サンプルにしない：EAT・WAKE・REST・ERODE・INTERRUPT・SURVIVAL・AVOID・GRUDGE・SLEEP・DIARY（シムの動きには残す）。
- 理由：食べる・起きる・休むは本番に当たるものがなく、100日ログでサンプルの半分近く（1203件中548件）を占めていた。

#### 9.5-2 向き（シム由来サンプル）

- シムのサンプルでは、**相手の側を actor、感情が動く側（perspective）を target** にそろえる（相手が起こした出来事、または二人のあいだで起きた出来事として書く）。
- target_category はすべて **「相棒へ」**。
- 「ほかの人へ」「利用者自身へ」は評価セットと実データで扱い、**評価セットには必ず含める**。
- 感情が動く側の**見えるふるまい**（謝った・距離を取った等）は書いてよいが、気持ちや増減は書かない（漏れ禁止はそのまま）。
- §1 の総則は実データと本番のために残す。
- 理由：v0.4 の決め方のままだと、相手のいる出来事の57%（655件中372件）が「ほかの人へ」になる。シムには二人しかおらず、相手は第三者ではない。エンジンの表では「ほかの人へ」はずっと弱い出来事として扱われている。

#### 9.5-3 §3の一覧（凍結対象）

- state_before が正解に効く種別は5つ：NOTICE（相手への支配的な気持ち・0.7以上の上乗せ）、LOST_SIGHT（支配的が好意か不安か）、REACT/avoided（近づいた気持ちが怒りか）、CONTACT/greet（自分の支配的）、CONTACT/keep_distance（自分の支配的が不安か）。§3 はこの一覧で確定する。
- 履歴で正解が変わる種別はない（慣れは §9.3-3 の欄、根に持つは §9.3-2 で除外）。
- recent_context はシムの正解に効かないので、§6 の「2割は欄を付けたまま学習」でだけ付ける。
- v0.4 の見当との違い：REACT は恨みを読まない（読むのは状態）。見失う・挨拶・距離を取るも状態を読む。謝罪は結果が文に出るので state_before は要らない。

#### 9.5-4 文に必ず出すもの

- 挨拶での相手の様子（にこやか／ふつう。greet_met と greet_calm を分けるため）
- 謝罪の結果
- 摩擦の強さ（§9.3-1）
- 距離を取ったのは誰か
- 「目が合った」か「見えた」か
- 型の選び方のテスト（同じ出来事に違う state を付けても型が変わらない）は、**感情が動く側の state** についてのもの。相手の見える様子は、出来事の一部として型を分けてよい。

#### 9.5-5 relationship

- シムでは全件同じ文（例：「同じ箱庭で暮らす相手。」）にし、**日数は入れない**（日数は日ごとに変わり、シムだけの手がかりになるため）。

#### 9.5-6 型

- 検証側にも専用の型を取り置く。種別×kind ごとに型は **3つ以上**（学習・検証・テストに1つ以上ずつ）。§2 と §4 をそろえた。

#### 9.5-7 版

- label_version は「正解の決め方の版」とし、仮の値を変えたら上げる。名前は仕様の版と分ける（§10.4：`rule-1`、`rule-2`…）。
- table_version は消し、generator_commit と config_hash に任せる。

### 9.6 あとで決めること（いつ・誰が）

- **エンジンのプリセットの係数の扱い**（時期：Phase 3 の前、監査②で先生が確認）：プリセットには、次元ごとの gain と、出来事の種類ごとの係数がすでにある（先生のプリセットは怒り 0.2・好意 0.35・疲労 0.4）。§6 の旧記述（「3段階の係数を持たせる作業が要る」）はこの実態に合わせて直した。決めるのは、**3段階（×0.5／×1.0／×1.5）に入らない値の扱い**（そのまま使う／3段階に寄せる／別建てにする）。
- **target_category の本番での意味のずれ**（時期：Phase 3 の前）：エンジン側の意味（利用者の言葉や気持ちが向く相手）と、仕様側の意味（働きかけを受けた側）がずれている。本番でどちらにそろえるか。
- **慣れの回数の、本番（会話の出来事）での数え方**（時期：Phase 3 の前）：§9.3-3 の数え方はシムの接触の定義であり、会話の出来事にどう当てるか。§6 の `contact_streak` の本番での扱いもここで決める。
- **学習側の target_category の偏り**（時期：Phase 2 の工場を設計するとき。案はきなこ、確認は先生）：シム由来は全件「相棒へ」のため、工場側で「ほかの人へ」「利用者自身へ」にあたる出来事を混ぜるかを決める（§10.3）。
- **ぷゆんの手間の見積もり**（時期：評価セットに着手する前。先生とぷゆん）：評価セットまわりの手間を見積もる——問題文の書き下ろし・書き直し（ぷゆん分 120件＋きなこの叩き台の書き直し 90件＝210件）、ラベル 300件で約6〜10時間、学習用 abstain 200件の作成。

## 10. 追加の決定（ぷゆんの決定、2026-11-21 夜）

先生の v0.5 確認（決定は漏れなく入っている、§1の例の点数も新しい手順で合っている）と、きなこの気づき3点への決定、先生の小さな直し。本節が §9 までの該当箇所を上書きする。本版（v0.6）で凍結する予定。

### 10.1 摩擦の点数

- シムの中では、摩擦の怒りは今の案どおり **2・5・8** で動かす（怒りのいちばんの種なので、動きは弱めない）。
- **正解を作るときだけ**、強さの段階（軽く1・ふつうに2・強く3）を、怒りの「係数の前の点数」として使う。§9.4 の手順に明記した。摩擦の信頼（−2）は今までどおり。
- 正解の例（係数 ×0.5／×1.0／×1.5 の順）：軽く **1／1／2**、ふつうに **1／2／3**、強く **2／3／4**。

- 理由：2・5・8 のままでは、±3 に収めた時点で「ふつうに」と「強く」が同じ正解になり、文から強さを読む練習にならない（§9.3-1 の目的と逆）。シムの点数を 1・2・3 にすると、怒りの増え方が今の半分以下になり、喧嘩や謝罪の場面がほとんど起きなくなるおそれがある。段階を 1・2・3 に当てるのは、エンジンの表の弱・中・強（だいたい1・2・3）と同じ考え方。

### 10.2 ラベルを付ける人に気質を見せない

- 理由：「気質の文は無視して」と頼むより、見せないほうが確実（係数の二重掛けを防ぐ）。監査②まで待たず、いま入れる。
